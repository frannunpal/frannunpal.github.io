Cities — Three.js (R3F) Architecture

Rendering 3D de ciudades con @react-three/fiber (R3F) + drei + postprocessing, reemplazando el anterior sistema Deck.gl v9 + MapLibre GL.

Migración completada 2026-07-25. El sistema anterior (deck.gl) está archivado en cities-deckgl-theatre. Esta página documenta la arquitectura actual.

Stack

@react-three/fiber  → React renderer para Three.js (Canvas R3F)
@react-three/drei   → OrbitControls, Sky, Stats (componentes utilitarios)
@react-three/postprocessing → SSAO, Bloom (efectos post-proceso)
three               → THREE.js core (geometría, materiales, shaders)
zustand             → State management (citiesStore, citiesUIStore)

ProcessingQueue — Sistema de Cola Secuencial

Singleton global que ejecuta tareas async una a una. Dos tareas principales:

TareaNombreEfectoOrigen
cache-load”Loading city from cache…”Intenta cargar GLTF de IndexedDBEffect 19
geometry-generate”Building city geometry…”Construye geometría Three.js desde ceroEffect 13

GLTF Cache Status

Actualmente DESHABILITADO. El cache-load detecta si hay entry.gltfBuffer en IndexedDB pero no lo carga — siempre deja que geometry-generate construya la geometría desde cero. Motivos:

  1. El GLTF export no preserva vertex attributes (buildingId, buildingHeight) necesarios para selection/hover/scanner
  2. Race condition con geometry-generate en el singleton ProcessingQueue
  3. GLTF corruptos o vacíos causaban “todo blanco”

El GLTF cache write sigue funcionando (fire-and-forget) para uso futuro cuando se resuelvan estos issues.

Canvas — Always Mounted

El Canvas R3F se monta siempre desde el inicio de la app. No se condiciona con isCityReady.

Antes (deck.gl): {isCityReady && <ThreeMap />} → Canvas se creaba/destruía → riesgo de WebGL context loss en cada generación.

Ahora: <ThreeMap /> siempre en el DOM → WebGL context se crea UNA vez y vive toda la sesión. El LoadingOverlay de Mantine cubre visualmente el canvas hasta que la geometría está lista.

Frameloop

frameloop="always" — antes era "demand" pero causaba WebGL context loss durante generación con Web Worker: los progress updates (30+ cambios de store en <1s) disparaban StoreInvalidator → invalidate() → ráfaga de renders → GPU sobrecargada → context loss.

Con "always", el render loop es continuo y suave, evitando la sobrecarga por ráfagas.

Merged Building Geometry

Un solo BufferGeometry para TODOS los edificios (en lugar de 2000+ draw calls individuales):

buildings[] → buildMergedBuildingGeometry()
  ├── Por cada building:
  │     ├── NaN guard → skip
  │     ├── createExtrudeGeometry(footprint, height)
  │     ├── vertex attributes: color (height-based), buildingId (index), buildingHeight
  │     ├── toNonIndexed() (requisito para mergeGeometries)
  │     └── push a geometries[]
  │
  └── mergeGeometries(geometries, false) → 1 BufferGeometry

Material: mergedBuildingMaterial (ShaderMaterial custom)
  ├── ComputeWindowPattern → ventanas procedurales (grid, floor bands, hash-based variation)
  ├── Scanner (uEnabled) → dot grid + sweep en fragment shader
  ├── Selection dimming → uSelectedIds / uHoveredId
  ├── Sun lighting → uSunDir, uSunColor, uAmbientStrength
  ├── Fog → fogColor, fogNear, fogFar
  ├── EnvMap reflection → windowReflectionIntensity, camera position
  └── Opacity → unselectedOpacity para selection context

Scanner Effect

El scanner en Three.js usa ShaderMaterial (no LayerExtension como en deck.gl):

  • buildingScannerMaterial.ts — ShaderMaterial con uniforms: uTime, uEnabled, uDotColor, uScanColor, uScanSpeed, uDotDensity, uDotOpacity, uBuildingHeight, uScanRangeMax, uOpacity
  • ScannerMesh en ThreeRenderer — componente R3F que recibe el mesh, geometría, scannerParams, y maneja useFrame para uTime
  • mergedBuildingMaterial.ts — integrado: uEnabled uniform activa el scanner dentro del shader principal de los edificios merged
  • Sin conflicto con shadows: Three.js maneja nativamente castShadow/receiveShadow, el ShaderMaterial tiene customDepthMaterial para shadow pass

Error Recovery

Geometry task falla
  → setGeometryError(msg)
  → geometryEnqueuedRef = false (permite reintentar)
  → UI muestra: "Failed to build city view" + botón Retry
  → Retry → callGenerate() → nueva generación completa

Stores

citiesStore (1314 líneas)

Zustand con persist middleware v9. Estado principal de la app Cities.

Campos clave para Three.js:

  • sceneNodes — árbol de escena (no persistido en rAF)
  • buildings, mapData — datos de generación (no persistidos)
  • sunAngle, sunElevation, sunColor — animados por useDayNightCycle

  • fogEnabled, fogColor, fogDensity, fogNear, fogFar — fog
  • skyTurbidity, skyRayleigh, skyMieCoefficient, skyMieDirectionalG — sky
  • scannerEnabled, scanColor, scanSpeed, dotColor, dotDensity, dotOpacity — scanner
  • ssao*, bloom* — post-processing
  • threeFlyToTarget — fly-to en Three.js
  • selectedPropertyGroup — Theatre property browser

citiesUIStore

Sin persist. Estado UI: selectedBuildingId, hoveredBuildingId.

Lo que Funciona ✅

  • Vista 3D con buildings, roads, parks, river, sea, coastline
  • Canvas R3F siempre montado (WebGL context persistente)
  • CitiesTheatre — panel inspector 100% Mantine
  • Hover/selection con opacidad reactiva
  • Scanner cyberpunk effect (shader)
  • Camera orbit/zoom/pan + fly-to
  • Lighting (ambient + directional + hemisphere + sky)
  • Shadows (directional light + PCF)
  • Fog (THREE.Fog reactivo)
  • Sky atmosférico (Preetham via drei)
  • SSAO + Bloom post-processing
  • Ciclo día/noche con sun position astronómico
  • Opacity controls por capa (Buildings, Roads, Parks, River, Sea)
  • Building filters (categorical, numeric slider)
  • Progress overlay durante generación
  • Error recovery con botón Retry
  • Web Worker generation con fallback main thread
  • IndexedDB cache (solo write, load deshabilitado)

Lo que NO Funciona ❌

  • GLTF cache load — deshabilitado (vertex attributes no preservados, race condition)
  • Farolas/emissive windows nocturnas — implementado en shader (uWindowEmissiveIntensity) pero con valores por defecto desactivados
  • Ventanas procedurales — shader implementado, parámetros expuestos en Theatre
  • Multiple workers — solo 1 worker para generación
  • Geocoder search — era Mapbox, no migrado a Three.js
