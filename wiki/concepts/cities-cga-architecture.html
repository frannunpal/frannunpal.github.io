1. CGA Shape → TypeScript Concepts

Direct mapping from the “Procedural Modeling of Buildings” paper (Müller et al., 2006) to TypeScript abstractions in this library.

2. Design Decisions

2.1 Why Scope3D and not AABB

The paper defines scope as an Oriented Bounding Box (OBB): an origin P plus three orthogonal unit vectors X/Y/Z plus a size S. This is fundamental for:

  • Angled roofs (not aligned with world axes)
  • Paper’s Petronas Tower: 45° rotated cube
  • Comp("faces") extracts 2D scopes aligned to each face’s normal — impossible with AABB

2.2 Why shapes are never deleted

The paper is explicit: replaced shapes are marked as inactive, never deleted. This is necessary for:

  • Occlusion queries against parent shapes ("noparent" subset)
  • Queries against active shapes vs. full history ("active" vs. "all")
  • The derivation tree for debugging

2.3 Why priority-based and not depth-first

The paper justifies breadth-first derivation by priority: guarantees the model evolves from low detail to high detail in a controlled way. Depth-first would generate fine details in one corner before having the building’s mass complete.

2.4 Why AttributeRegistry injectable (no singleton)

Two component instances with different cities must be able to have different attribute registries. A shared singleton would make this impossible. The injectable pattern also facilitates testing (empty registry or with mocks).

2.5 Why seed: string | number throughout the system

The seed as a string (city name) flows from GenerationParams to each SeededRandom of each attribute. Each attribute’s seed is composite: "${cityName}-${buildingId}-${attributeId}". This guarantees:

  • Same city → same buildings
  • Same building → same IP, same manager
  • Different attributes from same building → independent values

2.6 Why straight skeleton only convex in MVP

The complete Aichholzer/Eppstein algorithm for concave polygon straight skeleton is O(n log n) and non-trivial. For MVP, rectangular footprints (simple lots) are convex. Full implementation planned for Phase 5.

5. CGA Shape Grammar Contract (executive summary)

A Shape is: { id, symbol, scope: Scope3D, active: boolean, isTerminal: boolean, meshData?: MeshData[] }

A RuleDefinition is: { id, priority, predecessor, condition?, probability?, actions: RuleAction[] }

A RuleAction can be:

  • subdiv — divide scope by axis with absolute or relative sizes (r)
  • repeat — tile along an axis; repetitions = ⌈size/tileSize⌉
  • comp — extract faces/edges/vertices as aligned 2D scopes
  • instance — insert terminal mesh (cube, quad, cylinder, file)
  • translate / rotate / scale — transform current scope
  • push / pop — scope stack
  • snap — snapping to global construction planes
  • roof — generate roof geometry and create child shape
  • terminal — mark shape as terminal (no more rules)

A RuleCondition can be:

  • occ — occlusion query (none/part/full) against octree subset
  • visible — sightline visibility toward street/target
  • param-compare — guard on numeric parameter (h > 9)
  • scope-size — guard on scope dimension (scope.y > 3)

The RuleEngine loops: selects the active non-terminal shape whose rule has highest priority → evaluates condition → selects rule (stochastic) → applies actions → marks shape as inactive → adds successors. Terminates when no active non-terminals remain or maxIterations reached.
